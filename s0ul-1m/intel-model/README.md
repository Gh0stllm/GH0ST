# S0UL Intel numeric observation head

This is a **new, independent 25-parameter linear model** for a bounded
chain-native observation router. It is not the original 984,192-parameter S0UL
language model, a fine-tune of that model, or evidence that the language model
can analyse markets. The original checkpoint and deployment remain unchanged.

All live observations, feature calculations, inference and report rendering are
performed by the intelligence contracts. The caller supplies a registered
subject ID, not prices, feature vectors or a verdict. `classify` is a public pure
function, so its output is meaningful only when bound by the report controller
to the actual frame produced by `S0ULObservations`.

## Training and scope

`train.py` actually fits a four-input, five-output linear layer using PyTorch
Adam, float64 CPU arithmetic, 2,200 steps, and a fixed 8,192-example training set.
It learns synthetic policy score targets: an eligible observed change's absolute
basis-point magnitude competes with a 250-basis-point baseline. The export uses
int16 weights at scale 1,024 and integer biases quantized to one basis point.
The 250-basis-point baseline is an explicit product policy, not a learned market
risk threshold. It is fixed for this version.

The training examples are **synthetic numeric observations generated by the
included script**. They contain no market outcomes, news, social posts or live
off-chain analytics. Training is a reproducible predeployment activity. This
version does not implement on-chain training.

After quantization, all 8,192 training examples, 4,096 independently seeded
held-out examples, and 291 boundary/quality cases match the explicit teacher
policy. This measures recovery of that synthetic policy only. It is not
profitability, prediction, alpha, real-market generalization, or contract-audit
accuracy. A deterministic router could implement the same policy more cheaply;
the model provides a small, reproducible on-chain learned-head integration for
future observation policies, with its additional cost measured separately.

## Input and result

The input is the `int32[8]` vector defined in `S0ULIntelTypes.FeatureFrame`:

| Index | Meaning |
| --- | --- |
| 0–2 | Signed relative changes of reader values 0–2, clipped to ±10,000 bps |
| 3 | V2 reserve1/reserve0 ratio change, clipped to ±10,000 bps |
| 4 | Registered account's share of current supply, in bps |
| 5 | Elapsed seconds, capped at 86,400 |
| 6 | Reader kind: supply=1, watched balance=2, V2=3 |
| 7 | Quality flags: history=1, fresh=2, reader OK=4, zero baseline=8, clipped=16 |

The adapter selects only eligible magnitudes: supply uses `abs(x0)`, watched
balance uses `abs(x0)`, and V2 uses `abs(x2)` for LP supply and `abs(x3)` for the
reserve ratio. Account share and elapsed seconds remain factual report fields;
this model does not assign risk meaning to them. Reserve deltas are not volume,
LP supply is not a dollar liquidity valuation, and the reserve ratio is
denominated in the pool's quote token, not automatically USD or a TWAP.

| Label | Meaning |
| --- | --- |
| 0 | `normal`: no eligible change exceeds the version's baseline |
| 1 | `supply_change` |
| 2 | `watched_balance_change` |
| 3 | `pool_liquidity_change`: LP supply change |
| 4 | `pool_price_change`: reserve-ratio change |
| 5 | `insufficient_history`: deterministic eligibility abstention |

For V2, the larger eligible magnitude determines the selected observation.
Exact score ties choose the lower label. Direction is always taken from the
actual signed frame; the model does not manufacture a numeric fact or forecast.

Missing history, stale data, a failed reader, or any zero-baseline flag produce
label 5 before neural scoring. This is an explicit deterministic guard, not a
model confidence estimate. Clipped vectors are allowed, but reports must retain
the clipping flag and cannot rank uncapped magnitudes from capped inputs.

Scores are raw integer discriminants, not probabilities or confidence
percentages. Inactive labels are masked to `-(2**120)`. Invalid ranges, reader
kinds or flag bits revert with `InvalidFeatureVector`.

## Provenance and validation

The Solidity model exposes `modelId()`, `trainingManifestHash()`, `weightsHash()`
and `trainingDataHash()`. Hashes are SHA-256 of the exact respective JSON file
bytes. The training-data digest covers reproducibly generated rows; the full
training set is regenerated rather than duplicated in the repository.

`modelId` is SHA-256 of the UTF-8 prefix `S0UL_INTEL_OBSERVATION_V1`, followed by
the 32-byte weights digest and 32-byte training-manifest digest. Those identities
bind model policy and provenance; they do not certify market skill.

Run training/export with:

```sh
python3 s0ul-1m/intel-model/train.py
```

Verify the exported artifact using the independent, stdlib-only integer
reference:

```sh
python3 s0ul-1m/intel-model/reference.py
```

`parity-vectors.json` supplies 419 exact score/label vectors plus six rejected
vectors for separate EVM tests. `training-report.json` records Python training
and evaluation, and explicitly makes no claim that EVM parity has passed; that
evidence belongs to the contract test report.
