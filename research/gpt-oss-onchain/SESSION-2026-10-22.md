# GPT-OSS component optimization · 22 October 2026

This follow-up investigates the arithmetic and state formats needed for eventual on-chain GPT-OSS inference. The measured work uses synthetic inputs and local EVM transactions. It does not load or run the GPT-OSS model. The final evidence summary is [hour-session-validation.json](evidence/hour-session-validation.json).

## Selected results

| Component / workload | Comparison | Selected result | Interpretation |
| --- | ---: | ---: | --- |
| Eight 2,880-element row products | 3,895,428 gas across eight previous-kernel transactions | 1,240,994 gas in one eight-row call with predeployed weight code | **68.142% less gas** for this measured synthetic workload |
| Same new eight-row kernel, weights supplied in calldata | — | 1,427,509 gas | Separates the calldata-fed implementation from persistent weight-code access |
| Store 2,880 existing 16-bit values, first write | 65,707,799 gas using sign-extended int256 slots | 4,184,083 gas using packed words | **93.632% less write gas**, 2,880 data slots → 180 |
| Read and hash the same stored vector | 7,608,969 gas | 456,852 gas | Same serialized 16-bit payload and digest |
| Select the four largest of 32 random integer scores | 199,505 gas using our full-sort control | 46,391 gas using streaming top-4 | **76.747% less gas** versus this control; input-dependent |

The eight-row comparison combines arithmetic changes, shared-input batching and predeployed weight access. It includes the difference between eight transactions and one. It must not be described as a pure matrix-multiply instruction speedup, a full GPT-OSS saving or a Robinhood mainnet fee measurement.

The selected eight-row code path uses a 12,241-byte immutable local data shard, including its STOP prefix. Its recorded creation cost is **2,699,836 gas**. Compared with feeding weights to the new kernel in calldata, this data-shard cost amortizes after **15 repeated calls** for this dense fixture. Engine deployment is also a separate one-time cost. Sparse fixtures have different amortization. Neither figure is an estimate for deploying an entire model.

## What changed

### Scalar kernels

The first sweep tested loop unrolling, packed-word reads, optional zero-block checks and compiler optimizer settings. It kept the numerical operation fixed and selected candidates on two deterministic dense fixtures before testing separate held-out inputs. The best initial candidate used 327,031 gas on average on those training fixtures.

A second sweep factored repeated decode work into a helper and tested biased versus signed lookup tables. The selected scalar helper averaged **311,200 gas** on the same training fixtures. Opcode traces on a separate dense fixture show calldata loads falling from **2,977 to 457** and conditional jumps from **2,272 to 202** versus the previous kernel. The biased lookup experiment was slower and remains in the evidence.

### Eight lanes inside one EVM word

The vector kernel losslessly transposes the four-bit weight codes across eight rows. Each 256-bit word carries eight independent 32-bit accumulation fields. For twice the signed FP4 value `v` and an int16 activation `x`, it computes with unsigned quantities:

```text
w = v + 12                     # 0..24
u = x + 32768                  # 0..65535
D = sum(w * u)                 # per lane, 32 terms
W = sum(w)
X = sum(x)
dot = D - 32768 * W - 12 * X
```

The largest biased lane sum is `32 * 24 * 65535 = 50,330,880`, below `2**26`. A 32-bit field therefore cannot carry into its neighbour. The supported group/scale limits also keep each final signed Q32 row accumulator below the documented int256 bounds.

The decoder maps the original E2M1 codes without changing their represented values. A polynomial/bitwise implementation reduced decode work relative to the first Boolean version. Caching packed words, testing several unroll factors and factoring the decoder into a helper produced the selected `HelperLaneMxfp4.sol` implementation.

The implementation supports exactly eight rows, up to 180 groups of 32 values, signed-int16 operands and encoded scales 96–160. It does not supply an activation quantizer or reproduce all BF16 rounding behaviour.

### Nine-lane experiment

Nine 26-bit fields also fit in a 256-bit EVM word and satisfy the same biased-sum bound. The nine-row prototype uses lossless, unaligned 36-bit columns and a different frame layout. It passed the recorded arithmetic checks, but its extra packing and decoding overhead made it slower per output row than the selected eight-row implementation. More lanes alone did not improve the selected result.

### Packed state

The state-format experiment stores sixteen existing 16-bit values per storage word and reconstructs the same byte payload. It tests odd vector lengths, word boundaries, first writes, overwrites and resets, plus every possible 16-bit payload pattern.

This applies when the numerical policy already uses 16-bit values, including storage of raw BF16 bits. It does not convert or compress arbitrary int256/Q32 intermediates. The control deliberately uses int256 storage cells; Solidity already packs uint16 storage arrays, so these savings must not be advertised as a comparison against that automatic packing.

### Top-4 routing selection

`RouterTop4.sol` retains only four winners while scanning 32 integer scores. Ties select the lower expert index. The reference sorts all 32 scores. Tests include full-range signed integers, all-minimum/all-maximum values, ordering extremes, deliberate ties and held-out fuzz cases.

The random fixture saved 76.747%; the other recorded fixtures ranged from approximately 20.953% to 88.991%. This is a comparison with our control. It does not implement the router's weight matrix or gate softmax, and the tie policy still needs comparison with the intended full-model reference.

## Validation and provenance

The completed session passed all **13 validation suites**, all **109 compiler/layout configurations**, and **275,131 recorded validation cases across prototypes**. The dedicated persistent-code suite checked **1,858 fresh local weight shards** across **96 shape/data classes** and rejected **63 invalid calls**. These counts include repeated cases across separate implementations; they do not represent unique model prompts.

Each evidence report pins the tested contract's SHA-256. `session-summary.mjs` verifies those identities, requires every report to finish successfully, checks the original published baseline remains byte-identical and rejects unresolved failure artifacts. Counts aggregate cases across several implementations; they are not independent model prompts or language-quality evaluations.

The scalar and lane winners are each checked against all 256 encoded byte values at all 65 supported scales. Tests also cover signed input extremes, maximum supported group counts, reversible packing, invalid lengths, invalid scales and incorrect weight-code hashes. Selected suites add one-hot input positions; batch wrappers have separate shape tests. Additional fuzz sampling varies groups, signs, density and magnitudes. Storage tests cover all **65,536 distinct 16-bit payloads**. A separate persistent-code suite deploys fresh immutable data shards and checks the selected code-reading path against the CPU reference.

All gas results come from successful local Ganache Shanghai transaction receipts, including intrinsic/calldata gas and applicable storage refunds. The chain ID is 31337. Gas is independent of host execution speed; elapsed host benchmark time is not being presented as EVM throughput. Random local account addresses can change address-argument calldata gas by small increments.

The original deployed S0UL model, its mainnet executor and the production frontend were not changed by this work.

## Reproduce

Dependencies are pinned in the package files. The lockfile now marks Ganache's macOS-only bundled `fsevents` dependency optional; a clean Linux `npm ci` succeeded after the correction.

Run these in dependency order. An expired deadline skips the extra timed fuzz loop while retaining the deterministic sweeps and exhaustive cases. Supply a future UTC ISO timestamp to repeat a longer fuzz session.

```bash
npm ci --ignore-scripts --no-audit --no-fund
node session-optimize.mjs --deadline=1970-01-01T00:00:00Z
node session-experiments.mjs
node session-batching.mjs
node session-lanes.mjs --deadline=1970-01-01T00:00:00Z
node session-lanes.mjs --decoder=polynomial --deadline=1970-01-01T00:00:00Z
node session-lane-cache.mjs --deadline=1970-01-01T00:00:00Z
node session-lanes.mjs --decoder=polynomial --lanes=9 --deadline=1970-01-01T00:00:00Z
node session-lane-cache.mjs --lanes=9 --deadline=1970-01-01T00:00:00Z
node session-decoder-helper.mjs --deadline=1970-01-01T00:00:00Z
node session-decoder-helper.mjs --lanes=9 --deadline=1970-01-01T00:00:00Z
node session-state.mjs
node session-router.mjs --deadline=1970-01-01T00:00:00Z
node session-code-path.mjs
node session-summary.mjs
```

The longer run's exact counts and finish timestamps are in the committed reports. A shorter reproduction naturally records fewer additional fuzz cases. Solc 0.8.30, via-IR and the per-report optimizer settings are authoritative.

The code-path command defaults to five minutes of fresh local data-shard tests. Pass `--deadline=<UTC ISO timestamp>` to choose a different end time.
