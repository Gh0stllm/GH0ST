# Native GH0ST AEP accounting and payment draft

Status: source-backed draft, not approved, accepted, deployed or paid. No agent has contacted the Foundation or accessed a key. The full [current AEP agreement](https://docs.arbitrum.foundation/aep/ArbitrumExpansionProgramTerms.pdf) remains linked for operator review; the summary is not a replacement for its terms. It requires 10% of positive protocol net revenue, including relevant sequencing/bridge revenue, and contains continuing payment/information obligations, indemnification and Cayman dispute terms. No upfront license payment was identified. Deployment, settlement, transfer and hosting costs still exist.

## Actual official router support

The [official deployment guide](https://docs.arbitrum.io/launch-arbitrum-chain/chain-config/costs/aep-router-contracts) identifies `RewardDistributor` plus `ChildToParentRouter` contracts, and the [official fund-distribution repository](https://github.com/OffchainLabs/fund-distribution-contracts/tree/9d5714b6dffb52cc3c9981aa7e74c2a91f213348/src/FeeRouter) provides their current source. This bounded read pins commit `9d5714b6dffb52cc3c9981aa7e74c2a91f213348` (2026-10-29); file hashes and source links are in `aep-source-pins.json`. This pin has not been substituted into another team's deployed artifacts or compiled in this task.

`RewardDistributor` supports native value when its token argument is the zero address. Its recipient weights can allocate 9000/10000 to the operator and 1000/10000 to the router. On GL3, native value is GH0ST, so this route does not require inventing a wrapped GH0ST ERC-20 on GL3. The current implementation divides the available reward by 10000 before multiplying recipient weights; sub-10000-base-unit dust stays in the contract. Calculate and report actual distributed amounts and residual dust, rather than assuming every call transfers an exact real-number percentage. Failed native recipient transfers can go to the configured fallback recipient; those funds remain an accounting liability and must not silently be treated as operator profit.

`ArbChildToParentRewardRouter` routes native value through `ArbSys(0x64).withdrawEth(parentChainTarget)`. Despite that historical function name, the native currency on the child is GH0ST. With both token-address constructor fields set to the native-only sentinel `address(1)`, it skips ERC-20 gateway registration and uses the native withdrawal path. The actual GL3 native bridge must bind that withdrawal to the correct escrowed GH0ST on Robinhood. This is source support for the first hop, not an executed deployment or withdrawal claim. `DistributionInterval` limits routing frequency; a native receipt attempts routing automatically, and retained balance can be routed after the interval.

## The remaining GH0ST target decision

The official guide lists the Ethereum Foundation multisig `0x1Afa41C006dA1605846271E7bdae942F2787f941`, plus ETH-configured routers on Nova and Base. It does not list a Robinhood GH0ST router. That Ethereum address must not be copied into the RH target field without confirmation. For a non-ETH L3 gas token, the guide explicitly instructs operators to confirm the target with the Foundation. No RH-specific payment address or ETH exchange/payment arrangement is verified in this packet.

GH0ST is represented as an ERC-20 on Robinhood, while it is native value on GL3. The first hop can use native GL3 withdrawal. A second Robinhood-to-Ethereum ERC-20 hop would require an actual compatible token/gateway representation; it cannot be inferred just because Robinhood is Arbitrum. The operator must obtain the accepted RH recipient/router or another agreed payment mechanism/currency. This is a specific payment-routing decision, not an assumed need to negotiate a different license. No external reply-time estimate is invented.

## Accounting draft

Use receipts and ArbOS collector readback, not explorer fee estimates, to build a public period ledger. Record the actual chain IDs, block ranges/hashes, fee collector addresses, receiver changes, all reward distribution events, native withdrawals, RH claim receipts and any fallback distributions. Keep actual amounts as integer base units and state the token decimals and currency for every column.

For the standard component approach, apply the 10% allocation to execution base, execution surplus and parent-chain surplus reward collectors; keep genuine batch-poster cost recovery separate. Do not deduct parent settlement costs a second time from revenue that already excludes cost recovery. Track additional bridge/ordering revenue separately so it does not disappear from the calculation. The [official fee formula](https://docs.arbitrum.foundation/calculate-aep-fees) and [fee-reporting guide](https://docs.arbitrum.io/launch-arbitrum-chain/chain-config/costs/reporting-on-fees) explain these distinctions. If using gross-minus-cost accounting instead, reconcile all four components and documented settlement/DA costs once.

RH expenses are in ETH and GL3 collections in GH0ST. Never subtract their integer amounts directly. Preserve actual ETH receipts, batch-posting reports, the configured exchange-rate source/version and GH0ST reimbursement amounts. Avoid using an artificially inflated reimbursement rate to hide revenue as posting cost. Hosting/validator/proof CPU is not a listed settlement deduction. If an ETH payment is agreed, its valuation and payment receipts need an auditable reconciliation to the GH0ST-denominated liability.

Before payment routing is approved, reserve the calculated liability in a clearly identified account/escrow and report it as outstanding, not paid. Reserving funds is not claimed to satisfy the agreement's prompt-payment requirement. Confirm the actual accepted destination and operating payment cadence before declaring AEP payment setup complete. No burn-based zero-share exemption is assumed.

## Reviewable deployment parameters

`aep-payment-plan.example.json` contains immutable router/distributor parameter choices and unknown fields as null. An operator must approve the actual recipient, owner, fallback escrow and timing; supply an accepted native-GH0ST payment target or alternate agreed route; review full terms; and then use separate reviewed deployment transactions. This packet has no executable sender or automatic conversion/payment.
